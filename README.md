# 5-Stage Pipelined RISC Processor

A synthesizable, 5-stage pipelined RISC datapath (classic MIPS-style
encoding) in Verilog, with a dedicated hazard-detection/forwarding
unit and a self-checking testbench. Verified end-to-end with
ModelSim and Icarus Verilog in this environment (26/26 checks pass).

## Pipeline

```
IF -> ID -> EX -> MEM -> WB
```

- **ISA**: R-type (`add`, `sub`, `and`, `or`, `slt`), `addi`, `lw`, `sw`, `beq`.
- **Forwarding** (`rtl/forward_unit.v`): EX/MEM->EX and MEM/WB->EX
  bypass for ALU operands, so back-to-back ALU-dependent instructions
  run with **zero stall cycles**. A second set of paths feeds the
  **ID-stage branch comparator** (EX-ALU->ID, EX/MEM->ID, MEM/WB->ID),
  so `beq` resolves in decode with correct operands even when it
  depends on the immediately preceding instruction.
- **Hazard detection** (`rtl/hazard_unit.v`): detects the one hazard
  forwarding can't fix — a load whose result is needed by the very
  next instruction — and stalls exactly one cycle (PC + IF/ID frozen,
  ID/EX bubbled to a NOP).
- **Branch handling**: resolved in ID, so only one wrong-path
  instruction is ever fetched; it's squashed by flushing IF/ID
  (see the design note below on why ID/EX doesn't also need
  flushing here).

## File layout

```
rtl/
  defines.vh        opcode/funct/ALU-op encodings, forwarding-select constants
  pc_reg.v           program counter (stall / branch-target mux)
  instr_mem.v        instruction memory ($readmemh from program.hex)
  reg_file.v         32x32 register file, r0 hardwired to 0
  sign_extend.v      16->32 bit sign extension
  control_unit.v     main decoder (ID stage)
  alu_control.v      ALU op decoder (EX stage)
  alu.v              ALU (add/sub/and/or/slt + zero flag)
  data_mem.v         data memory (MEM stage)
  hazard_unit.v       load-use hazard detection / stall
  forward_unit.v      EX-to-EX, MEM-to-EX, and ID-branch forwarding muxes
  if_id_reg.v / id_ex_reg.v / ex_mem_reg.v / mem_wb_reg.v   pipeline registers
  pipeline_top.v      top-level datapath wiring it all together

tb/
  program.asm         assembly test program (see below)
  assemble.py         tiny 2-pass assembler -> program.hex
  program.hex         assembled machine code (regenerated by run_sim.sh)
  tb_pipeline_top.v   self-checking testbench

run_sim.sh            assembles the program and runs the testbench (Icarus)
```

## Running it

```bash
./run_sim.sh
```

This assembles `tb/program.asm`, compiles all RTL + the testbench with
Icarus Verilog, and runs it. Expected tail of output:

```
RESULT: ALL 26 CHECKS PASSED
```

A `sim/pipeline_wave.vcd` waveform is also produced (viewable in
GTKWave, or import into ModelSim's wave viewer) for inspecting
register write-back timing and stall/flush behavior cycle-by-cycle.

### Running in ModelSim instead

```tcl
vlib work
vlog +incdir+rtl rtl/*.v tb/tb_pipeline_top.v
vsim -c tb_pipeline_top -do "run -all; quit"
```
(Copy `tb/program.hex` next to wherever you launch `vsim` from, since
`instr_mem.v` reads it via a relative path — or edit `IMEM_FILE` in
the `pipeline_top` instantiation.)

## What the testbench actually verifies

`tb/program.asm` is organized into the same categories called out in
the project description, and `tb_pipeline_top.v` checks each one by
inspecting architectural register/memory state after the program
drains, plus internal stall/flush signal counts:

1. **Single-cycle correctness** — one instruction of each type.
2. **Back-to-back RAW hazards** — `add`/`sub`/`and` chained directly
   off each other's results; checks that EX/MEM and MEM/WB forwarding
   produce the right values **and** that `stall_pc` never asserts for
   these (zero-stall claim).
3. **Load-use hazard** — `lw` immediately followed by a dependent
   `add`; checks the correct value is produced **and** that exactly
   one stall cycle occurs.
4. **Branch corner cases** — not-taken, taken (with the two
   speculatively-fetched post-branch instructions squashed), and a
   branch whose operand is produced by the immediately preceding
   instruction (the case that needs the extra EX-ALU->ID forwarding
   path). Also checks that a squashed instruction never manages to
   commit a register write (write-back integrity).

## Design note: why only IF/ID is flushed on a taken branch

Because `beq` resolves combinationally in ID, by the time the branch
outcome is known only **one** instruction has been speculatively
fetched (it's sitting in IF, about to latch into IF/ID). Flushing
IF/ID squashes exactly that instruction — a full 1-cycle branch
penalty, no more, no less. The instruction already latched in ID/EX
at that moment is the one *before* the branch, which is on the
correct path and must not be squashed. `id_ex_reg.v` does have a
`bubble` control input, but it's driven by the hazard unit's
load-use stall, not by the branch signal — using it for both would
correctly cost you nothing extra here, but wiring the raw
branch-taken signal into it would risk squashing the wrong
instruction in a different hazard/branch pipeline configuration.

## Synthesis notes

- `data_mem.v` uses a combinational (asynchronous) read for
  simplicity in simulation; for FPGA targets where you want it to
  map to block RAM, switch to a registered read port and adjust the
  MEM-stage timing accordingly.
- Everything else here is plain structural/RTL Verilog-2001 and
  should synthesize as-is in Vivado, Quartus, or Yosys.
